\# Continuous Learning Workflow



\## Task 73 — Design the Continuous Learning Workflow



\### 1. Objective



The Adaptive MAS RCA system shall use engineer feedback from completed

root-cause analyses to continuously improve future RCA performance.



The continuous learning workflow consists of:



1\. Multi-agent RCA execution

2\. Engineer review of the RCA result

3\. Feedback submission

4\. Feedback persistence

5\. Knowledge-base update for validated incidents

6\. Aggregation of agent performance feedback

7\. Optional agent contribution-weight adjustment

8\. Improved future RCA through updated historical knowledge



The workflow is designed so that validated feedback becomes reusable

knowledge without directly modifying the underlying LLM model after

every individual feedback event.



\---



\## 2. Current System Components



The workflow uses the following existing components:



| Component | Responsibility |

|---|---|

| Incident | Stores the incident being investigated |

| AgentOutput | Stores output generated by an RCA agent |

| ConfidenceScore | Stores confidence associated with an agent output |

| Feedback | Stores engineer validation of an RCA output |

| Feedback API | Receives engineer feedback |

| Knowledge Base Updater | Adds validated incidents to the knowledge base |

| ChromaDB | Stores historical incident embeddings |

| Neo4j | Stores relationships between historical incidents and RCA knowledge |

| LangGraph | Orchestrates the RCA agents |

| Engineer UI | Allows engineers to review RCA and submit feedback |

\## 4. Feedback Trigger



The continuous-learning workflow is triggered when an engineer submits

feedback for an RCA agent output.



The frontend sends the feedback to:



```text

POST /api/feedback/

```



The feedback request contains:



\- user identifier

\- agent output identifier

\- rating

\- comments

\- correctness decision



The backend validates the referenced user, agent output, and incident

before storing the feedback.



\---



\## 5. Feedback Event Data



The existing database model stores the core feedback event.



Conceptually, a feedback event is represented as:



```json

{

&#x20; "feedback\_id": "UUID",

&#x20; "user\_id": "UUID",

&#x20; "incident\_id": "UUID",

&#x20; "output\_id": "UUID",

&#x20; "agent\_name": "metrics\_analysis\_agent",

&#x20; "is\_correct": true,

&#x20; "rating": 5,

&#x20; "comments": "The identified metric anomaly matches the incident.",

&#x20; "confidence": 0.91,

&#x20; "timestamp": "2026-09-22T10:30:00"

}

```



\### Data relationships



The `incident\_id`, `agent\_name`, diagnosis and recommendation are

obtained through the associated `AgentOutput`.



The confidence value is obtained from the associated `ConfidenceScore`.



Therefore the logical relationship is:



```text

Feedback

&#x20;  |

&#x20;  +-- output\_id

&#x20;         |

&#x20;         v

&#x20;    AgentOutput

&#x20;         |

&#x20;         +-- incident\_id

&#x20;         +-- agent\_name

&#x20;         +-- diagnosis

&#x20;         +-- recommendation

&#x20;         |

&#x20;         v

&#x20;    ConfidenceScore

&#x20;         |

&#x20;         +-- score

```



No additional feedback table is required for this workflow.

\## 6. Feedback Processing



After feedback is submitted:



```text

Engineer Feedback

&#x20;      |

&#x20;      v

Validate User

&#x20;      |

&#x20;      v

Validate Agent Output

&#x20;      |

&#x20;      v

Find Associated Incident

&#x20;      |

&#x20;      v

Persist Feedback

&#x20;      |

&#x20;      v

Check is\_correct

```



\### Correct feedback



If:



```text

is\_correct = true

```



the diagnosis is treated as engineer-validated.



The incident can then be marked as resolved and the validated incident

can be passed to the knowledge-base updater.



\### Incorrect feedback



If:



```text

is\_correct = false

```



the feedback is stored for future performance analysis.



Incorrect feedback must not automatically be inserted into the validated

historical knowledge base.

\## 8. Agent Performance Feedback



Feedback is accumulated rather than changing agent behavior after a

single feedback event.



For each agent, the system can calculate:



```text

Total Feedback

Correct Feedback

Incorrect Feedback

Correctness Rate

Average Rating

Average Confidence

```



For example:



```text

Metrics Analysis Agent



Total feedback:       50

Correct:              46

Incorrect:             4

Correctness rate:     92%

Average rating:      4.5

```



These statistics provide an empirical measure of historical agent

performance.



\---



\## 9. Agent Contribution Weight Adjustment



Agent contribution weights may optionally be adjusted using accumulated

feedback.



The system should not immediately change an agent's weight after one

feedback event.



Instead:



```text

Feedback Events

&#x20;      |

&#x20;      v

Aggregate Statistics

&#x20;      |

&#x20;      v

Agent Performance

&#x20;      |

&#x20;      v

Check Minimum Feedback Threshold

&#x20;      |

&#x20;      v

Calculate Updated Contribution

&#x20;      |

&#x20;      v

Apply Weight Adjustment

```



A minimum number of feedback observations should be available before

automatically changing an agent's contribution.



This reduces the effect of individual noisy or incorrect feedback events.



The weight-adjustment mechanism is an optional extension of the

continuous-learning workflow and should remain separate from the

knowledge-base update.

\## 12. Learning Safety Rules



The continuous-learning mechanism follows these rules:



\### Rule 1 — Explicit validation



Only feedback explicitly marked as correct is eligible for validated

knowledge-base insertion.



\### Rule 2 — No immediate weight changes



A single feedback event should not automatically change an agent's

contribution weight.



\### Rule 3 — Historical feedback is retained



Feedback remains stored so that agent performance can be evaluated later.



\### Rule 4 — Incorrect feedback is useful



Incorrect feedback is retained for performance analysis and failure

analysis but is not treated as validated RCA knowledge.



\### Rule 5 — Knowledge and model learning are separate



The initial continuous-learning mechanism updates historical knowledge

and performance statistics. It does not retrain or modify the underlying

LLM after every feedback event.
